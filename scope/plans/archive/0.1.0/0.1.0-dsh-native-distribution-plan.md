## 1. 产品定义

摸鱼工具箱不再是"嵌入 DSH 的工具箱"，而是一个基于 DeepSeek Harness 构建的桌面
发行版：

- DSH 是应用本体、默认界面和 Agent Runtime；
- Electron 提供桌面宿主与目标平台原生能力；
- 图片、PDF、条码、截图等原有功能成为 Moyu DSH 扩展；
- 扩展同时提供模型可调用的 Tool 和用户可操作的 Client UI，二者共享同一 Service；
- MCP 用于外部服务，不作为 Moyu 内部能力的桥接协议。

第一阶段只完成 macOS arm64；Windows x64 能力和发布约定保留，后续适配。

## 2. 上游接口既定事实

核验日期 2026-08-19，对象为 npm 发布包（`@deepseek-ai/dsh@0.1.0-rc.7` 及其闭包）。
这些结论已经复核过，不作为 M0a 的待验证项。

| 事实 | 依据 |
| --- | --- |
| 上游 MIT 许可，公开仓库 `github.com/deepseek-ai/deepseek-harness`（monorepo，`apps/cli`、`packages/client/ui-*`） | 包内 LICENSE 与 `repository.directory` |
| 前端无需我们构建：`@deepseek-ai/dsh-web-frontend@0.1.0-rc.7` 发布的就是完整 dist，约 4.62 MB / 91 文件，`exports: {"./dist/*"}` | 包元数据；`dsh-web-app` README 明确"frontend dist must be built，无 source-serving fallback" |
| Client 插件加载机制：Host 扫描 composition 中声明 `dsh.client` 的包，解析其 `exports["./client"]`，哈希进 boot graph，由 `/plugins` 提供 | `@deepseek-ai/dsh-client-modules` README |
| 包契约：一个包同时是 Host 插件（`.`）与 Client 插件（`./client`），并声明 `dsh.client.{inject, platform}` | `@deepseek-ai/dsh-client-ui-sidebar/package.json` |
| Client bundle 格式：`window.__ModuleLoader__.load({ id, factory: (require) => … })`，懒 CJS 工厂、扁平模块图、externals 走 `require` 表、第三方依赖内联 | 同包 `lib/client.js` |
| 官方插件构建工具是公开的 `tsdown`，源码是 TSX；我们的 Client 插件可以正常使用 TS/JSX | 同包 `scripts.bundle` |
| Client 侧 React peer 版本是 `^18.2.0` | 同包 `peerDependencies` |
| 上游凭据默认实现落盘为明文 YAML `$DSH_HOME/.credentials.yaml`，优先级低于继承环境变量 | `@deepseek-ai/dsh-credentials-local` README |
| dist-tag 不可依赖：多数子包 `latest = 0.0.1-rc.1`、`next = 0.1.0-rc.7`；包会改名（`dsh-frontend` → `dsh-web-frontend`，`dsh-frontend-static` → `dsh-host-frontend-static`，旧名已 404） | npm dist-tags 与 404 实测 |

由此得到两条工程约定：

1. 所有 `@deepseek-ai/*` 依赖显式钉版本号，禁止依赖 dist-tag；升级是一次性整批
   bump 加 lockfile 更新。
2. 兼容测试必须覆盖"包是否仍然存在、是否改名"，不只是"接口是否仍然可用"。

M0a 剩下的**客户端 bundle 格式风险**是：我们用 tsdown 产出的 Client bundle 能否通过
DSH 的 bundle purity gate。上游 MIT 且公开，先读 `packages/client/ui-sidebar` 的构建
配置，不做黑盒试错。（决策 20 收窄：产品现在只有 `@moyu/dsh-plugin-screenshot` 一个
client bundle——composer 截图按钮；image/pdf 已退为纯 Host Tool，无 client 导出。）

但它不是 M0a 的唯一上游风险。以下三项同样直接决定架构，必须一并作为 M0a 硬门禁，
不得推迟到实施中发现：

| 门禁 | 失败后的影响 |
| --- | --- |
| Client plugin 能否提供独立功能页/路由 | **结论（2026-08-20）**：机制是 `conversation.view`（list slot，占满会话主体，tab 切换，`ui-trajectory` 同款）。自有 URL 路由不可，但无需 patch 或 fork。**渲染尚未实测**：hello 已注册该 slot，实测时我方 tab、上游 trajectory tab 与 chat tab **三者都不出现**——会话已创建（输入框在）但视图环需会话有内容，取决于真实模型回合。判别性对照说明不是我方注册问题，故与真实模型回合并入同批，挂 M1 签字 |

## 3. 目标架构

```text
Electron Desktop Host（main）
├── 主 BrowserWindow
│   └── DSH Web UI（唯一主界面，本地 DSH origin）
├── DSH Host Runtime（Electron 自带 Node 运行时的独立子进程）
│   ├── Moyu Profile（唯一产品 profile）
│   ├── Moyu Host Services（sharp / tesseract.js / pdf / barcode …）
│   └── Moyu Tools + Client Plugins
├── Narrow Desktop Bridge（进程 IPC，有类型、仅白名单 RPC）
├── 截图采集与 overlay / pin 窗口
└── 过渡执行环境
    ├── legacy renderer 窗口
    └── headless job renderer
```

### 3.1 进程模型

DSH Host 以 Electron 自带运行时的独立 Node 子进程运行，不使用外挂 Node runtime，也不放进
Electron 主进程：

- 插件、Agent 循环或 Host Service 崩溃不带走桌面宿主；
- **main ↔ Host 的控制与桌面桥链路**是子进程 IPC，只承载有类型的白名单 RPC，不需要端口、Bearer Token、
  认证或重连管理；
- 只有一套 Node ABI，`sharp` 沿用现有 Electron 构建与 `asarUnpack` 配置，不再准备
  第二份原生模块。

进程 IPC 的免认证结论**只适用于这一条链路**。UI ↔ Host 是独立的第二条链路，
见 §3.2。

原生资产按性质分三类，不混为一谈：

| 资产 | 性质 | 需要验证的事 |
| --- | --- | --- |
| `sharp` | `.node` 原生模块 | DSH 独立 Node 子进程下的 Electron ABI 加载、`asarUnpack` 路径、签名 |
| `tesseract.js` | JS + WASM + Worker + 语言数据 | Worker 创建方式、WASM 与 `@tesseract.js-data/*` 语言包在 asar 内的解析路径（当前经 `require.resolve` 定位，未列入 `asarUnpack`），macOS 打包后实测 |
| FFmpeg | 独立可执行文件 | macOS arm64 产物获取与校验、独立签名与公证、许可声明；见 7.5 |

M0a 需分别记录 DSH Host 的**安装依赖闭包**与**实际运行加载闭包**中的 `.node` 模块。
禁用 pty/terminal 只保证不加载，不保证不安装（`node-pty` 一类仍可能在依赖树里）。
进程模型的复核以运行加载闭包为准；安装闭包用于包体核算与签名清单。

### 3.2 两条通信链路

必须分开设计，不能用一条的结论覆盖另一条：

```text
链路 A（控制/桌面能力）  Electron main ──进程 IPC──> DSH Host(Electron Node 子进程)
链路 B（应用数据）       DSH Web UI ──carrier──> DSH Host
```

链路 B 的上游事实（`dsh-host-webserver`、`dsh-host-apiproxy` README）：

- API 网关（`ctx.apiProxy`）**不自带路由**，传输由 carrier 决定：host 侧
  `toFetchHandler`，client 侧 `AbstractApiClient` + 平台子类；
- HTTP 只是其中一种 carrier。上游明确写着：*"This server serves browsers only;
  Electron loads dist over `file://` and carries fetch over an IPC bridge."*
- HTTP carrier **没有 TLS、认证与 origin 策略**（上游 Known Limitations 原文），
  `trustedHosts` 是 DNS rebinding 防护，不是客户端认证；
- 绑定只接受 `127.0.0.1` 或 `0.0.0.0`，我们只允许前者。

因此 M0a 必须先在两种 carrier 之间做出选择：

| 方案 | 优点 | 需验证 |
| --- | --- | --- |
| B1 `file://` + Electron IPC carrier（**倾向**） | 无监听端口，本机其他进程无法访问；无 origin/认证问题；恢复语义简单 | 客户端平台子类能否在不重建上游 frontend dist 的前提下替换；dist 在 `file://` 下能否加载 |
| B2 loopback HTTP/WS | 与上游 Web 形态一致，风险已知 | 端口分配、ready 信号、崩溃恢复、Origin 校验、是否加每次启动随机凭证 |

M0a 收口结论：**采用 B2 + A 路径认证**（Electron 网络层注入随机 token，Host 侧
route/upgrade 前置 fence 校验），未 patch 上游。证据见 `m0a-dsh-native-spike.md` §6。

#### fence 必须 fail-closed

当前 fence 通过猴补丁 `http.createServer` 并包裹 `server.on('upgrade')` 实现。上游
webserver 只提供 `register` / `registerUpgrade` / `registerFallback`，没有"所有路由之前"
的中间件接缝，因此这是当下唯一可行做法。但它的失败形态是 **fail-open**：上游一旦改用
`addListener('upgrade')`、`once`、`node:https`、`http2` 或不经 `http.createServer` 创建
服务器，fence 会静默失效，而端口、UI 一切正常。

因此必须成对实现：

1. **启动自检**：Host ready 之后、主窗口显示之前，主进程对本代 origin 发一个**不带
   token** 的请求，必须收到 403 才继续；否则视为 fence 未生效，直接进降级页，不展示 UI。
   HTTP 与 WebSocket upgrade 各测一次。
2. **兼容探针**：把该自检纳入 `verify:compat`，上游改写服务器创建方式时先响在探针，
   而不是发行后。

若 M0a 判定只能走 B2，则必须同时定稿：

- 端口分配（`port: 0` 由 OS 指派）与 Host ready 信号的具体形式；
- Host 异常退出后主窗口的恢复策略（重启 Host、页面重连、失败进降级页），
  不允许停在白屏或静默失效的页面；
- 主窗口侧的 Origin/Host 校验；
- **是否为每次启动注入随机凭证**。如果不加，必须在计划中写明接受的威胁模型：
  同机任意进程可访问该端口，可读写会话、触发工具与消耗凭据。默认立场是加。

### 3.3 主窗口与 origin 策略

主 BrowserWindow 直接运行 DSH Web UI，不再有"Vanilla 应用壳 + DSH
WebContentsView"的双层结构，也不使用 iframe 或 `<webview>`。

主界面是应用自带的本地 origin（B1 为 `file://`，B2 为 loopback HTTP），导航面必须由
主进程收口：

- `will-navigate`：只允许本地 DSH origin，其余一律拒绝；
- `setWindowOpenHandler`：默认 `deny`，外链走 `shell.openExternal` 并做协议白名单；
- `session.will-download`：接管，全部转入桌面桥的保存流程，不使用浏览器默认下载；
- 权限请求（剪贴板、媒体、通知、屏幕）默认拒绝，按产品需要逐项放行；
- DSH 自带的目录/文件选择器必须被 `desktop.pickFiles` / `desktop.pickDirectory`
  接管。**桥提供方法不等于 DSH 会用它**，M0b 要验证的是实际接管生效。

采用 B1（`file://`）时，本节的 origin 约束改为"只允许应用自带 dist 的 `file://` 路径"，
导航、新窗口、下载与权限的接管要求不变。

所有应用内 WebContents 保持 `contextIsolation: true`、`nodeIntegration: false`、
`sandbox: true`。DSH UI 不需要 preload；legacy 与 headless job 各自使用独立最小
preload。

### 3.4 窄桌面桥

Electron 与 DSH Host 之间只提供有类型的窄桥：

```text
desktop.pickFiles
desktop.pickDirectory
desktop.saveResult
desktop.showItem
desktop.copy
desktop.requestScreenCapture
desktop.openLegacyExtension
desktop.secureStore / desktop.secureRetrieve / desktop.secureDelete
```

禁止通用 channel、任意 Electron API、任意脚本、任意 URL 和任意文件路径调用。
每个方法必须有 schema、调用主体、超时、取消、错误清洗和生命周期归属。

#### 三个方向（2026-08-20，M1-a2）

| 方向 | 用途 | 状态 |
| --- | --- | --- |
| Host → main | 桌面能力（对话框、剪贴板、Finder、凭据、legacy 窗口） | 已实现 |
| main → Host | `image.*` Host Service 调用，供迁移期 legacy 页面复用同一实现 | ✅ M1-a2 已实现 |
| Host → main → legacy renderer | 长任务的 `progress` 推送（非请求/响应） | ✅ M1-a2 已实现 |

`main → Host` 与进度推送的约束与桌面桥同级：固定方法集、结构化参数、generation 绑定、
超时、取消、错误清洗。补充两条：

- **Moyu `desktop.*` 文件能力只传令牌**：过桥只传 `fileId`（B3 的文件令牌）与结构化参数，实际读写由 Host
  侧按令牌解析。批量图片若传 buffer 会两次跨进程边界复制，直接爆内存。
- **DSH workspace 是受控例外**：DSH 内核的 session/workspace 契约使用 Host 内绝对路径；正式
  profile 只允许应用创建的 `$DSH_HOME/workspace`，不得由用户选择任意目录，也不得进入任何
  Moyu Tool 的参数、返回值、普通日志或 Client 页面状态。该例外不放宽 `desktop.*` 的 token-only
  规则。
- **Host 掉线即明确失败**：legacy 的图片转换原本自足，接入后依赖 Host 存活。Host 崩溃
  换代时在途 job 必须带可读原因失败，不得挂住。

**`main → Host` 是迁移期脚手架，不是长期架构。** 它只服务尚未原生化的 legacy 页面；
最后一个 legacy 图片入口删除时同步删除该方向（拆除条件写在 M3 完成定义里）。
不写死这条，它会慢慢长成本节一开始就要防的通用 IPC。

## 4. 权限与产品 Profile

Moyu 自建唯一产品 profile，不交付上游 shipped 的 `standard`、`code`、`minimal`、
`cordis` preset。发行版方案下这些 preset 属于上游 CLI 包的 `config/` 目录，我们
不安装该包，它们天然不存在。

正式包默认不提供（Moyu 默认 surface 不暴露的 Tool / 能力）：

- bash、pwsh、terminal、str_replace_editor 等 shell 类 Tool；
- 通用文件读写与搜索（tool-fs / tool-fs-search）；
- subagent（tool-subagent 系列）；
- 运行时动态插件定义与执行（`cordis_define` / `cordis_run` 一类，权限等价 shell）；
- 任意插件安装与动态加载（`cordis-host-runner` / `cordis-client-runner` 保持禁用——它们
  绕过 Tool 面直接拿到 `ctx.shell`，等价 shell）；
- 任何未列入产品清单的 Tool。

**已开启的 DSH 原生管理能力（M3 / 决策 20 后放开）**：preset 管理、plugin inventory 与
权限设置入口现在挂载——`agent-presets`、`ui-agent-preset`、`plugin-inventory`、
`ui-settings-plugins`、`ui-settings-plugin-inventory`、`permission`、`ui-permission` 七项
由默认禁用改为启用。放开前提是表面仍然干净：

- 上述入口只提供查看 / 切换 / 授权，不引入 shell 类 Tool；`tool-bash` / `tool-pwsh` /
  `terminal` 仍禁用，用户切换到的其它 preset 才能带进 shell 工具；
- `ctx.shell`（confined）由 base 的 `bash-sandbox` 提供（macOS 默认启用），permission
  插件据此工作，但**不**向 agent 暴露 bash Tool；`DSH_PERMISSION_MODE` 已移除，用户首次
  在 UI 里选择 full access 一次即可（原生审批卡）；
- `cordis-host-runner` / `cordis-client-runner` 保持禁用，杜绝绕过 Tool 面拿 shell。

安全不是"启动时检查一次"：

1. 构建产物只交付 Moyu profile；
2. 会话创建守卫（`@moyu/dsh-profile` 的 `assertMoyuToolSurface`）核对实际 Tool 全集：
   - 必备三件套（`image_convert`、`pdf_process`、`screenshot_capture`）必须都在——**contains
     语义**，允许其它 preset 带进 bash / subagent 等额外工具；
   - 当前预设为 moyu（默认）时，额外出现 shell 类工具直接拒绝创建会话；用户主动切换到的
     其它 preset 不拦；
3. Host 层继续用工作目录、文件会话与桌面桥白名单兜底；
4. 发现 Tool / preset 漂移时拒绝创建会话，进入安全降级页（诊断 + 重试）。
    降级页不提供"改用另一套界面"的出口——legacy 只是迁移期被 DSH 调起的功能窗口，
    不是可选应用壳。

以后如开放开发模式，必须作为独立高级模式设计，不复用正式 profile 的权限承诺。

## 5. 凭据

### 5.1 现状与问题

上游 `dsh-credentials-local` 的四层优先级为：继承环境变量 > `$DSH_HOME/.credentials.yaml`
> 项目 `.env` > 用户 `.env`。用户在 Models 页面填入的 Key 会以**明文 YAML** 落在
`.credentials.yaml`。`0600` 只能阻挡同机其他系统用户，挡不住同 UID 的其他进程或
Agent，对桌面发行版不可接受。

### 5.2 目标

新增 `@moyu/dsh-credentials-desktop`，实现 DSH 的 credentials provider 契约，后端
经 `desktop.secureStore` 系列方法调用 Electron `safeStorage`：

- 正式 profile 只装这一个 provider，不装 `dsh-credentials-local`；
- 明文不经过普通 renderer、日志与通用桌面 IPC；
- 继承环境变量层的行为保留与否需在 M0a 决定并写入文档（开发期便利 vs 产品一致性）。

**`safeStorage` 不是"凭据存进 Keychain"。** 它只提供 `encryptString` /
`decryptString`（macOS 下密钥由 Keychain 托管），**密文与元数据仍由我们自己保存**。
落盘模型必须在 M0b 前定稿，至少包含：

| 项 | 要求 |
| --- | --- |
| 密文位置 | `userData` 下的专用文件，不放进 `DSH_HOME`，避免与上游实现混淆 |
| 权限 | `0600` |
| 写入 | 临时文件 + `rename` 原子替换，不就地覆盖 |
| 删除 | `unset` 真正删除条目，不留残留密文 |
| 迁移 | 检测到旧 `.credentials.yaml` 时导入并**删除原文件**，记录一次迁移日志（不含明文） |
| 解密失败 | 由 DSH 统一主界面提示重新录入；不切换应用壳、不静默吞掉，也不回落明文层 |
| 可用性 | `safeStorage.isEncryptionAvailable()` 为 false 时拒绝保存并明确提示，不降级存明文 |

M0a/M0b 验收判据：UI 可完成 set / get / unset，且**全盘搜索找不到明文 Key**。

### 5.3 前置确认

credentials 基座是否允许第三方替换 provider，需要在 M0a 确认。若不可替换，退路
是向上游提 PR 或维护小型 patch，不接受直接沿用明文方案。

## 6. 调用主体、任务与结果模型

### 6.1 显式主体

现有实现有两套互相独立的身份假设，在主窗口易主后都会失效：

- `assertMainWindowSender(event)`：`src/main/index.js:203` 定义 1 处，**调用 41 处**
  （`grep` 总命中 42 = 1 定义 + 41 调用），断言"只允许从主窗口发起"。新架构下主窗口是
  DSH UI，它恰恰不该获得这些能力；legacy 页面成为独立窗口后会全部触发该断言。
- 会话所有权 `ownerId === event.sender.id`：另有 **13 处**引用，覆盖 format、
  illustrator、com、screenshot 等会话。

首个插件迁移之前必须抽象为显式主体：

```text
renderer:<webContentsId>
dsh:<sessionId>
legacy:<interactionId>
job:<jobId>
```

输入、结果、取消与保存权限按主体隔离。向模型返回 resultId、附件或结构化结果，
不默认暴露本机绝对路径。

### 6.2 分批替换，不一次迁完

41 处调用里包含 Windows/COM 专属路径（`com:*`、`illustrator:*`、`office:*`），Mac 阶段
无法做打包实测。一次性改完等于把不可验证的回归混进 M1。分批规则：

1. 先引入统一的 caller/capability 校验层（一个入口，按主体查授权），不改调用点语义；
2. 只迁移 M2 必需的 macOS 路径（`format:*`、`pdf:*`、`image:*`、`screenshot:*`、
   `recovery:*`、`shortcut:*`）；
3. Windows 专属调用（`com:*`、`illustrator:*`、`office:*`）保持等价行为，或整体推迟到
   Windows 阶段，届时以 Windows 打包产物实测为准；
4. 每批迁移都要说明验证方式；不能实测的批次不得声称完成。

### 6.3 任务形状

耗时任务统一异步：

```text
submit → jobId → progress/status → resultId
```

图片批量、OCR、PDF、视频不得把长计算塞进一次同步 Tool 调用。取消必须传播到
Worker/子进程，应用退出时统一清理。

## 7. 功能迁移分类

### 7.1 包装型

已在主进程/Worker、可较直接抽成 Host Service：

- sharp 图片转换（`apps/desktop/main/index.js` 的 `format:*` 一线，纯 sharp 路径 macOS 可用）；
- tesseract.js OCR（需补 3.1 表中的 WASM/Worker/语言数据打包验证）。

### 7.2 移植型

主要逻辑仍在 renderer，不能假设已有共享能力层，每片单独 Spike、估时与验收：

- PDF：`pdf-lib` 可直接下沉；`pdfjs-dist` 的 Node 入口与 renderer 不同；`qpdf-run` 的公开
  runner 是 browser-only，底层另含 qpdf WASM。两者的 Host 路线已由 M2 资产 Spike 定稿；
- 条码：`jsbarcode` / `opentype.js` / `gs1encoder`，算法层可整块复用；注意
  `gs1encoder` 是 Emscripten 模块，靠 `import.meta.url` 相对加载同目录 WASM，
  换执行环境时要重新验证解析路径；
- **Fabric 画布：已按决策 15 切出 0.1.0 迁移范围**（2026-08-21）。`legacy/renderer/board/**`
  实测 6152 行（scene / canvas / guides / history / overlay / editor 子系统）加 Fabric 事件
  体系，移植代价远超收益。处理方式：
  - 0.1.0 **不迁移、不重写、也不删除**——`board/**` 与 `fabric` 依赖原样留在 legacy；
  - 过渡期从 DSH 内的入口调起受限 legacy 窗口（B4b 已有链路，零新增成本）；
  - 将来在 DSH 基础上**重新构建**为原生功能，按新底座重新设计，不以移植为目标。

### 7.2.1 legacy 的产品定位（2026-08-20 校正）

**legacy renderer 不是可选应用壳。** 应用启动路径唯一：始终进入 DSH。未配置凭据时由
DSH 自身的配置引导承接，Moyu 不再自建"进入 DSH / 打开传统工具"的二选一首屏
（B4a 已删除该实现）。

尚未迁移的功能只能**从 DSH 内部入口调起**，以功能窗口形式出现：DSH 内的入口 →
`desktop.openLegacyExtension(module)` → 打开对应 legacy 窗口（自带受限 preload，
不获得 DSH Host 权限）。用户不应感知到"另一套软件"。

### 7.3 headless renderer job

迁移期允许受控 headless renderer job：

- 只接受固定 job schema；
- 使用独立最小 preload，绝不复用主 UI preload；
- 不执行任意脚本、URL 或 DOM 指令；
- 有并发上限、超时、取消、崩溃恢复与进程清理；
- 不直接读写文件，输入输出仍由 Host / 桌面桥会话化提供；
- 适合下沉的纯计算逻辑最终迁入 Host Service。

### 7.4 截图的三段拆分

截图不是一件事，三段归属不同。**决策 15 后截图进入 M2**（此前写的"不进第一批"已作废，
那时画布与截图被一并排除；现在排除的只有画布与 PDF organizer）：

| 段 | 现状 | 归属 |
| --- | --- | --- |
| 原生采集 | `build/macos/screen-capture`，已随 mac 包交付 | 包装型，留在 Electron main，经 `desktop.requestScreenCapture` 暴露 |
| 会话协议 | `screenshot:start` → `overlay-ready` → `complete`/`cancel`，owner 挂主窗口 sender | 必须重写为 Host Service + 显式主体 |
| overlay / pin 窗口 | 独立顶层 BrowserWindow（`apps/desktop/main/index.js` 内 overlay / pin 两处） | 保留为独立窗口，与"DSH 是唯一主界面"不冲突；preload 与主体身份重新定义 |

两条硬约束（截图与其它能力不同，它能主动读取屏幕）：

- **`screenshot_capture` 必须经明确的用户确认**，模型不得静默截屏。取消是正常结果，
  不作为错误（§4.2）。确认由 Electron 出，模型无法绕过；
- **图像数据走临时文件令牌**，不经 IPC 传大 Buffer——与 §3.4 "大二进制不过桥" 同一条理由。

OCR 不归入截图会话协议。`screenshot:ocr` 是历史入口；0.1.0 下沉时改为独立
`ocr_extract(fileId) -> text` 能力，截图完成后的"提取文字"只是人工入口调用它。这样 PDF
整页转图、图片转换结果和用户已有图片都能复用同一份 OCR Service；截图这一片只负责采集。

### 7.5 macOS FFmpeg

现有 FFmpeg 只随 Windows 发布（`getFormatToolPath` 在非 win32 直接抛错，
`build.mac.extraResources` 无 ffmpeg，下载脚本只有 `build:tools:win`）。macOS 上不存在
可包装的视频能力。若纳入 0.1.0，必须作为独立功能片完成：macOS arm64 产物获取与
校验、调用、独立签名与公证、许可声明、干净机器实测。不得与图片、OCR 并称"现成
包装型能力"。

## 8. 仓库结构与构建链

启用 npm workspaces，不引入第二套包管理器。

构建链分工：

- `electron-vite` 负责 `apps/desktop` 的 main / preload 与 `legacy/renderer` 的三个 HTML
  入口（`index` / `pin` / `screenshot`），配置里的输入路径随搬迁更新；

  `window.__ModuleLoader__` 懒 CJS 工厂格式；tsdown 是构建工具，不是第二套包管理器。

1. M0a 只新增 `packages/`，不动现有 `src/`；
2. M0b 再执行 `src/main` → `apps/desktop/main`、`src/preload` → `apps/desktop/preload`、

## 9. 上游跟进与版本策略

DSH 成为产品源码与 UI 后，不在用户机器上后台替换运行时核心。用户通过升级 Moyu
Tools 获得新版 DSH。

"不锁死版本"的定义是持续跟进上游：

- 开发时定期升级 DSH npm 包（显式版本号，见第 2 节）；
- CI 对候选上游版本执行兼容测试，覆盖包存在性、改名、Host/Client 接口与
  Tool 白名单；
- 每个可发布构建记录确定的 DSH 版本、lockfile 与依赖闭包；
- 上游升级失败不影响已发布应用启动；
- 不在启动时执行 `npx latest`，不动态替换核心 UI/Host。

依赖上游的方式：保持 Moyu 独立仓库、只用发布包。仅当 M0a 的 bundle purity gate
被证明无法在包外复刻时，才转入受控下游 fork。不得未经 Spike 把 DSH 整仓复制进
本仓库长期手改。

### 分层验证口径（2026-08-21）

打包是最贵的验证手段，只在真正涉及交付布局时使用。

| 层级 | 触发时机 | 内容 |
| --- | --- | --- |
| 日常开发 | 每次改动 | 相关 harness + 静态检查 + `npm run build` |
| 里程碑收口 | 一片完成 | `tests/run-acceptance.mjs` 显式清单中的全部当前有效 harness |
| 打包验证 | 见下方触发清单 | `build:mac` + 启动读日志 |

**必须打包的触发条件**（任一命中即需要）：

- 打包布局、`asar` / `asarUnpack`、`extraResources`、`afterPack` 变化；
- 原生模块（`.node`）增减或版本变化；
- 签名、hardened runtime、公证相关改动；
- **运行闭包变化**：`@deepseek-ai/*` 增减或升版、`build-dsh-runtime.mjs` 逻辑变化、
  profile 模板生成方式变化；
- **新增打包后需要解析路径的资源**：WASM、语言包、worker 脚本、外挂可执行文件。
  （§12 未决里的 `tesseract.js` 与 `gs1encoder` 都属于这一类；PDF 的 qpdf WASM 已完成一次
  dev/打包态 Spike，条码片仍需单独验证 gs1encoder。）

**"走 headless 就不用打包"要加条件**：只有**完全复用已验证的 headless 入口、preload 与
资源布局**时才免打包。一旦新增 renderer entry、preload、worker 或 `extraResources` 路径，
即使没有 `.node`，仍然命中交付布局门禁。`@napi-rs/canvas@0.1.100` 已在当前 macOS 包的
DSH runtime 中存在并加载成功；本次只是把它从传递 optional dep 升格为显式依赖，需登记
闭包与签名清单，但不因产品接线本身重复打包。

**不构成打包理由**：网络中断、会话/工具链故障、以及任何与产品代码无关的环境问题。
失败后先定位再决定，不重复盲打包。

已完成打包点：M0b fixed workspace provider、M2 PDF 资产路径 Spike。下一次排定打包点只在

### 功能验证 ≠ 交付验证（2026-08-21，两次事故的共同教训）

单元/专项 harness 直接加载插件源码或复用已存在的 profile，会**全绿但带病**。已实际发生两次：

| 事故 | 验证走的旁路 | 漏掉的真实路径 |
| --- | --- | --- |
| PDF 插件找不到 `pdf-lib` | harness 用已存在的老 profile | `ensureProfile()` 的首次复制/升级分支 |
| `screenshot_capture` 从未注册 | harness 直接 `import` 插件源码 | `cordis.patch.yml` 的 insert 块（插件根本没进 composition） |

第二次尤其说明问题：截图片 S1–S7 七个切片、30/30 harness 全绿，**没有一个能发现这个 Tool 压根没被注册**。

**因此每片收口必须至少有一条经真实 composition + 真实 profile 的验证**，而不是只有直接加载插件的
单元测试。`tests/verify-dsh-session-create.mjs` 是这类守卫的第一个实例：它经真实 UI origin 调
`/api/session.create`，钉住"Tool 白名单 == composition 实际注册集合"这个不变量。

同类推理错误也要避免：**「不在禁用清单」不等于「已启用」**。`tool-ask-user` 曾被当作"保留启用"，
实际上游 bundle 根本不含它，判断必须以 composition 实际内容为准。

## 13. 功能接入规范（2026-08-21 定稿）

一个功能在 DSH 里可以占五个面。**占面有成本，按规则挑，不是全占。**

### 13.1 五个面与选择规则

| 面 | 注册 | 谁用 | 什么时候占 |
| --- | --- | --- | --- |
| **Host Service** | `ctx.<name>` | 其它代码 | **永远占**。唯一业务实现，是另外四个面的共同后端 |
| **Tool** | `ctx.tools.register` | 模型 | 当"让模型替用户做这件事"有价值时占。判据：**参数能用一句自然语言说清楚吗**？说不清（拖拽、框选、精确坐标）就别占 |
| **Client UI** | `ctx.slots.register` | 人（点） | 当用户需要**不依赖模型**也能用时占（离线、精确控制、批量勾选） |
| **Command（斜杠）** | `ctx.commands.register` | 人（会话里敲） | **默认不占**。它是 human-command registry，与 agent 无关；agent 调用已由 Tool 覆盖，人的入口已由 Client UI 覆盖。只有"高频 + 参数一行写得完"才考虑 |
| **Skill** | `ctx.skills.registerProvider` | 模型（按需加载 `SKILL.md`） | 当模型需要**怎么组合调用**的知识时占：多步、有顺序、有陷阱。**单步工具不需要 Skill** |

成本提示：每多一个 Tool，schema 进每次请求前缀（token + KV cache）；每多一个 Skill，模型上下文多一份指南；每多一个 Command，人要多记一个名字。

**系统触发器不是第六个面。** 全局快捷键、Dock 菜单、托盘、URL Scheme 统一定义为**外部触发器**：
它们是入口，不是能力的实现面。触发器必须调用**同一个 Host Service**，不得复制一条平行的业务
链路；每类触发器有自己的调用主体（如 `system:globalShortcut`），与 `renderer:` / `dsh:` /
`legacy:` / `job:` 并列（§6.1）。

### 13.2 每个功能接入前必答的七问

1. 业务实现放哪？默认 Host Service，但**涉及系统能力的功能要分层**，不能笼统说"都放 Host"：
   - **Host Service**：会话、权限策略、状态机、结果归属；
   - **Electron main**：系统能力本身（ScreenCaptureKit、窗口、原生确认框、剪贴板）；
   - **交互窗口**（如截图 overlay）：只负责交互（选区、标注），不持有业务状态。
   否则会和 §7.4 的三段拆分自相矛盾。
2. 模型要不要能调？要 → Tool，并说明为什么值那份 schema 成本
3. 人要不要图形入口？要 → Client UI，挂哪个 slot（`conversation.view` / `settings.section`）
4. 人要不要会话里敲？默认否 → 不占 Command
5. 模型需不需要操作指南？多步才要 → Skill
6. 需不需要用户确认？要区分两类，**确认时机不同**：
   - **执行前确认**：操作会造成副作用时问一句（覆盖文件、批量修改）；
   - **读取前确认**：能力会读取用户环境时（截图读屏），**确认必须发生在读取动作之前**。
     现有截图流程是"先抓屏再显示 overlay"，因此 **overlay 不能充当模型调用的授权**——
     那时屏幕内容已经读完了。

   授权来源：
   - 人点按钮 / 按全局快捷键 → **该明确操作本身即授权**，不再弹确认；
   - 模型调用 Tool → **必须先由 Electron 显示确认**，用户同意后才允许调用系统能力。

   **不做 sticky consent**：每次模型调用都要确认。若确需高频，应是显式的"本次会话内允许"开关，
   不得隐式延续。

   **具体形式（2026-08-22 定）**：
   - **按钮路径完全不弹**——人点击即授权。区分依据必须是**入口结构**（只有页面够得着的路由
     vs 只有模型够得着的 Tool），**不得用调用方自称的参数**（如 `skipConsent`），否则模型迟早
     能把它置真，读屏前确认这道防线即失效。
   - **模型路径默认每次弹**，确认框上提供「本次会话内允许，不再询问」勾选：默认不勾、必须用户
     主动勾、作用域限当前会话、Host 换代即失效、只在内存不落盘。

   **不变量强度已降级，务必知悉**（2026-08-22）：S1 当初建立的是「**不存在裸采集方法**」——
   确认与读屏绑死在 `desktop.requestScreenCapture` 里，物理上无法绕过。为实现按钮路径免弹窗，
   现已新增无确认的 `desktop.captureScreen`，不变量降级为「**存在裸方法，但只有路由这一条
   路径调用它**」。

    当前实现安全：Tool 的 execute 用字面量构造 payload（`startFromTool({ scope })`），
    模型参数进不了 `start()`，schema 里也只有 `operation` / `job_id`。**`startFromUser()` /
    `startFromTool()` 两个函数已取代 `entry` 参数**（2026-08-22 落地，`index.mjs:189/195`），
    入口结构即授权：模型路径固定走带确认的 `requestScreenCapture`，按钮路径走免确认的
    `captureScreen`，安全性已由结构保证而非约定。遗留：补一条回归断言钉住
    "Tool 路径不得走 `captureScreen`"——该断言目前不存在，建议加进
    `tests/verify-screenshot-capture-tool.mjs`。
7. 输入输出怎么过桥？输入 `fileId`、输出 `resultId`、**大二进制禁止过桥**、不向模型暴露绝对路径。
   另外两条：
   - **`caller` 与 `resultSink` 分开声明**——谁发起，和结果归谁，不是同一件事（见 13.4）；
   - **结果保留期按能力声明，不是全局常量**。PDF/图片的 10 分钟适用于"提交即取"的节奏；
     截图是"随手截了回头再处理"，沿用 10 分钟就是 bug。过期策略必须在 UI 上可见。

### 13.3 这份规范的验证判据

**用截图这个功能验证它。** 截图与已接入的图片/PDF 形状不同：无文件输入、需用户确认、主动读屏。

- 不改这份规范就能把截图做完 → 规范成立；
- 做到一半发现规范没覆盖 → 就地补，补完才算数。

截图 S1–S7 已按这条机制做完：实现中补清了 `expired` 与 `cancelled` 的边界、
复用 overlay 的 reset 边界、三种 `resultSink` 路由、以及 `pin:<pinId>` 主体。
因此 §13 在 2026-08-21 转为当前正本；后续条码、格式工厂等功能按本节接入。

### 13.4 交互式采集能力的附加契约

普通能力是"参数进 → 结果出"。**交互式采集**（截图，将来的画布取样）中间夹着一段用户操作，
不能只套普通计算任务的 progress 语义。

#### 状态机

```text
awaiting_consent → awaiting_selection → processing → completed | cancelled | failed
```

- **Tool 不得同步挂住等人操作**，必须先返回 `jobId`，状态经 `status` 查询；
- `status` 表达的是"等待用户操作中"，不是计算进度；
- `expired` 是**结果状态**，不是会话终态：确认框没人点、overlay 没人选区都归入
  `cancelled`；只有已完成结果超过保留期，才显示 `resultStatus: expired`；
- **终态细分**，都属正常结束（§4.2 取消不是错误）：
  `cancelled_by_consent`（拒绝授权，模型不应重试）与 `cancelled_by_user`（放弃选区）
  语义不同，模型的后续行为也不同。

#### 并发与生命周期

- **同时只允许一个采集会话**；
- 重复触发返回 `busy`，**不抢占**已有会话；
- 复用型 overlay 窗口的生命周期不等于会话生命周期：进入新的 `awaiting_selection`
  会话前，必须由协议显式重置上一轮选区、标注、工具与临时状态，并在首帧绘制完成后再
  报告 ready；
- 关闭交互窗口、拒绝确认、超时，**一律是正常 `cancelled`**，不是错误；
- **Host 崩溃换代时**：关闭交互窗口、撤销会话、清除临时令牌，不留孤儿窗口。

#### caller 与 resultSink

| 触发方式（caller） | 结果去向（resultSink） |
| --- | --- |
| Tool（`dsh:<generation>`） | 当前 DSH 会话，返回 `resultId` |
| Client UI（`renderer:` / 插件界面） | 该插件自己的结果区 |
| 全局快捷键（`system:globalShortcut`） | **应用级临时结果区**，不自动塞进当前会话，也不再默认进 legacy 画布 |

全局快捷键路径的三条补充（理由：按快捷键时应用大概率不在前台）：

- **默认同时复制到剪贴板**——最高频的后续动作，且复制不消耗结果；
- **完成后不抢焦点**，交互窗口关闭后原样退回用户原来的应用；
- **保留期单独设定**（见 13.2 第 7 问）。

`pin` 只是人工后续动作：返回内部 `pinId`，**不暴露给模型**，模型可以截图但不能钉。
每个钉图窗口以 `pin:<pinId>` 作为调用主体，只能操作自己的 `pinId`；应用退出时必须显式关闭
全部 pin 窗口，避免顶层窗口残留。

#### 契约只写已实现的能力

首版 `screenshot_capture` 只表达"发起交互式截图"，**不写 `全屏 / 区域 / 指定窗口` 参数**——
当前真正具备的只有交互式区域选择，指定窗口没有完整链路。把不存在的能力写进 schema 比不写更糟：
模型会照着尝试，然后得到一串不可用的失败。

   并判定哪些必须替换。这条在 M0b 收口后仍然有效，不随 picker 问题的解决而关闭；
2. bundle purity gate 的确切规则：externals 白名单、允许内联的依赖范围（决策 20 后产品只有
   截图一个 client bundle，暴露面已大幅收窄）；
3. 继承环境变量凭据层在正式产品中保留与否（见 5.2）；

   `@napi-rs/canvas` 的 Windows 平台分包（如 `canvas-win32-x64-msvc`）如何进入 DSH
